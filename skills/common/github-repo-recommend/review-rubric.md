# 选型锐评标准

火力级别：**毒舌但讲证据**。允许说难听话，不允许说没根据的话。

和周榜锐评的差别：周榜回答「这周为什么火」，选型回答「我该不该依赖它」。
**热度在这里是次要指标**——star 数只能证明有人看过，证明不了半年后还有人修 bug。

## 一条锐评的构成

```
[判断] + [支撑数字] + [代价或前提]
```

长度：**1~3 句，80 字以内**。杀伤力来自精准，不是来自长。

「代价」这一段是选型报告和推广文的分界线。**每个 `首选` 都必须说得出它的代价**，
说不出来说明你没看懂它，或者你在写广告。

## 证据 → 判词映射

| 证据组合 | 可以下的判断 |
|----------|--------------|
| `found_by` 只有 `topic` 一路 + 品类明显不符 | 它自己贴了标签而已，不属于这个品类，剔掉 |
| `contributors_count` ≤ 10 + `owner_type` = Organization | 单公司项目，公司不做了就没有社区能接手 |
| `commits_last_90d` 比同榜低一个数量级 | 投入在收缩，用之前先去 commit 记录确认还有没有人管 |
| `age_days` < 365 + star 上万 + `contributors_count` < 40 | 热度和工程沉淀不匹配，方向可能对，时间不够 |
| `promo_markers` 含 trendshift + `age_days` 短 | 热度有运营成分，别把 star 当质量凭证 |
| `release_count` / `age_days` 极高（几天一个） | 迭代凶，但接口大概率还在漂，别做深度耦合 |
| `release_count` 长期为 0 | 没有版本纪律，只能钉 commit 用 |
| `license` 是 GPL/AGPL | 闭源商用的硬约束，**必须点名**，不能只写在角落 |
| `license` = NONE / NOASSERTION | 默认无授权，法律上不可用 |
| `open_issues` 数百 + `commits_last_90d` 稀疏 | 发完不管，issue 区在裸奔 |
| `open_issues` 个位数 + star 不高 | 不是维护得好，是用的人还太少，别当优点写 |
| README 短 + 无营销徽章 + 提交密集 | 少见的工程自信，可以正面说 |
| 贡献者多 + 提交密集 + 多年历史 + 宽松许可证 | 可以放心依赖，直接给「首选」 |

同一仓库命中多条时，挑**最影响选型决策的那条**，不要罗列。

### 口径说明（会把人坑到的字段）

`contributors_count` 和 `commits_last_90d` 都**只统计默认分支**，且 contributors API
**不认没绑定 GitHub 账号的提交邮箱**。所以低贡献者数只能推出「默认分支上可归属的工程活动少」，
不能直接推出「只有 N 个人在做」。要下更重的判断，先跑一条验证：

```bash
gh api "repos/<owner>/<name>/commits?per_page=20" --jq '.[] | [.commit.author.date, .commit.author.name] | @tsv'
```

`score` 是**筛选工具，不是质量评价**。它只知道相关性、活跃度、规模、规范度，不知道这东西好不好用。
报告里不要说「评分 98.6 所以推荐」——那是循环论证。

## 正例

真实数据（2026-08-12，关键字 `vector database`）：

**qdrant/qdrant** — 33.9k star / 186 贡献者 / 90 天 743 次提交 / README 11.5k 字符 / 无推广徽章

> 全场唯一 README 不到 12k 字符、不挂任何营销徽章的头部项目。186 个贡献者、90 天 743 次提交，
> 工程节奏稳。它把「别的都不做」当成了产品决策。

夸也挂数字，并且用「README 长度」「无徽章」这种反向证据支撑，而不是形容词堆砌。

**infiniflow/infinity** — 4.6k star / 52 贡献者 / 90 天 35 次提交 / 4 年 / 57 个 release

> 四年项目、57 个 release，技术路线是这批里最有想法的。但近 90 天只有 35 次提交，
> 比同体量项目低一个数量级，投入明显在收缩——用之前先去 commit 记录里确认还有没有人在管。

先给它应得的肯定，再用横向对比的数字点出风险，最后给一个可执行的动作。

**alibaba/zvec** — 15.4k star / 250 天 / 31 贡献者 / 10 个 release / trendshift 徽章

> 250 天冲到 15.4k star，但只有 31 个贡献者、10 个 release，README 挂着 Trendshift 徽章——
> 热度和工程沉淀严重不匹配。方向没问题，时间还不够。

把三个数字并排放，结论自己就浮出来了，不需要额外加形容词。

## 反例

| 写法 | 问题 |
|------|------|
| 「社区活跃，值得一试」 | 零信息，删掉 |
| 「star 最多，所以推荐」 | star 是关注度不是可靠性。改说贡献者数、提交频率、许可证 |
| 「综合评分 98.6，排名第一」 | 拿自己算的分数论证自己的推荐，循环论证 |
| 「这个项目要凉了」 | 指控但没证据。换成「90 天 35 次提交，比同榜低一个数量级」 |
| 「性能最好」 | 没跑过基准就别说性能。改说架构定位和适用规模 |
| 「生产可用」 | 谁的生产？改成具体条件：「几百万向量以内、单机部署可用」 |
| 只写优点不写 `avoid` | 推荐没有边界就是广告 |
| 一段 200 字分析 | 超长即失焦，砍到 2 句 |

## 边界

- **不猜动机**。可以说「数据像运营驱动」，不要说「作者刷星」。
- **不评价个人**。骂项目不骂人。
- **没跑过就别评性能**。这套数据里没有任何性能指标。
- **数据缺失就说缺失**。`contributors_count = -1` 表示 API 取数失败，此时不能拿它下结论。
- **国产项目不额外宽容也不额外苛刻**，同一套指标。

## 总结那句话

报告开头的 `summary` 要给一句能指导决策的横向判断，不是候选清单的复述。
2026-08-12 `vector database` 的实例：

> 108 个候选里真正是「向量数据库」的不到十个，其余多是 RAG 框架给自己贴了 vector-database 标签。
> 真要选型，先分清三档：Qdrant / Milvus / Weaviate 是有多年沉淀的服务端选手，zvec / HelixDB 是
> 热度远超工程沉淀的新面孔，Manticore / ObjectBox 则是别的品类顺手补了向量能力。
> 多数团队从 Qdrant 起步，规模真上来了再谈 Milvus。

要求：**给出分档逻辑和一个默认建议**。「各有优劣，按需选择」是没做功课的托词。
